# Errors and lessons

The errors found while building and auditing this series ([`forum-app-ci-testing`](https://github.com/CarpinetiOctavio/forum-app-ci-testing), [`forum-app-qa-pipeline`](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline) and this repository): what happened, how it was found and what was corrected. An error here is a statement that was false, a mechanism that did not do what was stated, a decision that reversed another without answering why it had been rejected, or a pipeline dependency out of support. Each entry says where it was found: **published** (on `main`, a tag, a `-legacy` repository or an original submission) or **found in review** (before the merge).

## A document said something the pipeline did not do

- **QA from `staging`, PROD from `main`.** *Published, cloud-deploy.* The pipeline rules mapped QA to `staging` and PROD to `main` without being checked against the constraint they served, build once and promote that image: each branch built its own image, so PROD would run one QA never tested. Designing the PROD stage exposed it. Both deploys now come from the same run on `main` ([ADR-009](decisions/ADR-009-single-build-trigger.md), [`1c2f988`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/1c2f988)) and take the digest of its single build ([ADR-007](decisions/ADR-007-render-deploy-mechanism.md), amendment of 2026-11-11).
- **A push trigger without its answer.** *Published, qa-pipeline and cloud-deploy.* Both repositories adopted `push` on `staging` and `main` without answering why ci-testing had rejected push and pull request triggers on the same branch, and this repository's rules still required `push` on `feature/**` only. The series audit found both. The rules now match `ci.yml` and give the answer: the ruleset requires a pull request with no bypass, so a direct push is rejected ([`29642e9`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/29642e9); qa-pipeline [ADR-004](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline/blob/main/docs/decisions/ADR-004-pipeline-extension.md), amendment of 2026-11-12).
- **Trigger descriptions out of date.** *Published, ci-testing and qa-pipeline.* ci-testing's README said the pipeline ran "on every push", its `COMMANDS.md` described a trigger removed in July and a direct push to `main` that the ruleset rejects, and qa-pipeline's README contradicted itself in two paragraphs. Found in the series audit; corrected in ci-testing's [`0dbfd7e`](https://github.com/CarpinetiOctavio/forum-app-ci-testing/commit/0dbfd7e) and [`a3fec10`](https://github.com/CarpinetiOctavio/forum-app-ci-testing/commit/a3fec10) and qa-pipeline's [`9fa4f10`](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline/commit/9fa4f10). Lesson: the trigger is stated in one place, `ci.yml` and its ADR, and linked from the rest.
- **Diagrams of an older pipeline.** *Published, ci-testing and cloud-deploy.* ci-testing's diagram showed the coverage command its ADR-004 documents as the bug, and this repository's was a copy of qa-pipeline's, with no Docker, registry or deploy stage. Found in the series audit and in the sweep before this repository's last block; redrawn ([`0dbfd7e`](https://github.com/CarpinetiOctavio/forum-app-ci-testing/commit/0dbfd7e), [`95b0304`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/95b0304)).
- **Rules that described another build.** *Published, cloud-deploy.* Rules carried over from earlier work were not checked against the build: `docker.md` required a statically linked backend, built with CGO for SQLite on `alpine`; `pipeline.md` named qa-pipeline's SonarCloud key after this repository had its own, and forbade parallel jobs without an ADR while both Docker builds ran in parallel. Found in the sweep before the last block; corrected in [`29642e9`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/29642e9).
- **A README about another repository, and names that moved.** *Published, cloud-deploy and ci-testing.* From August, this repository's README described qa-pipeline, the repository it was copied from; in ci-testing, after the rename, `forum-app-cloud-deploy` pointed to a different repository and a different ADR-008. Found in the series audit; this README was rewritten for `v1.0.0`, and ci-testing's ADR-000 and ADR-006 say which repository they meant ([`0dbfd7e`](https://github.com/CarpinetiOctavio/forum-app-ci-testing/commit/0dbfd7e)).
- **Configuration that changed without a record.** *Published, ci-testing and qa-pipeline.* ci-testing's ruleset was changed to require only `Test Summary` while its ADR-004 still described four individual checks, and qa-pipeline's SonarCloud key was created as `…pipeline2` while its ADR-002 said the key matched the repository's name. Found in the series audit; amendments of 2026-11-12 record the real configuration (ci-testing [ADR-004](https://github.com/CarpinetiOctavio/forum-app-ci-testing/blob/main/docs/decisions/ADR-004-ci-pipeline-design.md), qa-pipeline [ADR-002](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline/blob/main/docs/decisions/ADR-002-sonarcloud.md)). When the ruleset changed is not recorded.

## A number or fact that was not checked

- **"47/47 tests".** *Published, cloud-deploy.* A test count wrong from the first time it was written was accepted and spread to three documents: the suite has 50 tests. Found by rerunning the suite with a clean cache and counting; corrected in [`8878f6a`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/8878f6a). Lesson: a number a machine produces is linked to its source, not restated.
- **Figures with no source, and a deploy documented as something else.** *Published, cloud-deploy-legacy.* The original TP8 submission's README reported "Issues Resolved: 47" with no source, and documented a deploy mechanism different from the one implemented. Found in the audit of 2026-08-03 ([audit](audits/cloud-deploy-legacy-audit-results.md), §0 and §4); `-legacy` is not modified, and this repository started over from qa-pipeline ([ADR-000](decisions/ADR-000-starting-from-qa-pipeline-v1.0.0.md)).
- **Wrong dates for the series.** *Published, ci-testing and cloud-deploy-legacy.* ci-testing's README dated all three assignments to the second half of 2025, and `-legacy`'s README says "Year: 2025" while its banner says July 2026; TP8 was built in June and July 2026. ci-testing's README was corrected ([`a3fec10`](https://github.com/CarpinetiOctavio/forum-app-ci-testing/commit/a3fec10)); `-legacy` is not modified, and this README gives the dates.
- **Statements in ADRs that git does not support.** *Published, ci-testing and qa-pipeline.* ci-testing's ADR-004 called its first commit "the code the course handed out", which git cannot confirm; qa-pipeline's ADR-000 said ci-testing ran Node 24, when only its actions' runtime was at 24, and described `-legacy` ADRs that a later revert had removed. Found in the series audit; amendments of 2026-11-12 record what git shows (ci-testing [ADR-004](https://github.com/CarpinetiOctavio/forum-app-ci-testing/blob/main/docs/decisions/ADR-004-ci-pipeline-design.md), qa-pipeline [ADR-000](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline/blob/main/docs/decisions/ADR-000-starting-from-ci-testing-v1.1.0.md)).
- **Counts in qa-pipeline's README.** *Published, qa-pipeline.* It said "four extra jobs" (two), "20 mocked specs" (19, wrong from the commit that wrote it) and "React 18" (19), and presented as a gap a ruleset case that every job already covered. Found in the series audit; corrected in [`9fa4f10`](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline/commit/9fa4f10) and qa-pipeline's [ADR-004](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline/blob/main/docs/decisions/ADR-004-pipeline-extension.md), amendment of 2026-11-12.
- **A correction attributed to the wrong review.** *Published, cloud-deploy.* ADR-003 said the case against `latest` came from a review of qa-pipeline where `latest` appeared in a deploy configuration; it came from a correction to another student's work, and no deploy configuration in the series uses `latest`. Found in the closing review; corrected by an amendment ([ADR-003](decisions/ADR-003-image-tagging.md), 2026-11-24).

## A mechanism that did not do what was stated

- **A quality gate nobody waited for.** *Published, qa-pipeline and cloud-deploy.* The wait for the SonarCloud gate was left off while the gate failed for a reason later fixed, and was never turned back on: the job passed with the gate red (qa-pipeline `2c58765`, run `30714893286`), and this repository inherited it against its own rule that no image is built before every gate passes. Found in the series audit; the job now waits for the gate on the path to `main` (qa-pipeline [ADR-002](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline/blob/main/docs/decisions/ADR-002-sonarcloud.md), [ADR-009](decisions/ADR-009-single-build-trigger.md), amendments). A red gate blocking a pull request into `main`: [screenshot 14](screenshots/14-quality-gate-blocks-pr-into-main.png).
- **Background processes, and a pinned wait that broke.** *Published, qa-pipeline and cloud-deploy.* An ADR rejected `npm start &` over zombie processes, and the workflow then started the backend that way; and the Cypress action's own wait for the frontend began failing with "Socket closed" with no change to the pinned action. The failure surfaced here first and was reproduced in qa-pipeline (run `43374818876`); the frontend now starts in its own step and is waited for with `wait-on`, and the runner's log shows it terminates orphan processes ([ADR-010](decisions/ADR-010-cypress-frontend-wait.md); qa-pipeline [ADR-003](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline/blob/main/docs/decisions/ADR-003-cypress.md), amendment of 2026-11-12). Lesson: pinning an action does not pin the environment it runs on.
- **A tag treated as immutable.** *Published, cloud-deploy.* It was accepted that a SHA tag names one set of bytes, that builds were reproducible, and that rollback relied on tags never moving. Identical trees produced different digests (runs `43306631470` and `43341781168`, [screenshots 02 and 03](screenshots/README.md)), so a rerun moves the tag. Deploys and rollback go by digest ([ADR-003](decisions/ADR-003-image-tagging.md) and [ADR-009](decisions/ADR-009-single-build-trigger.md), amendments of 2026-11-23; [`29642e9`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/29642e9)).
- **"A newly built image" on every deploy.** *Published, cloud-deploy.* ADR-006 said each deploy reruns the frontend substitution on a newly built image; PROD and rollback deploy an image already built, and the substitution runs at each container start. Found while condensing the ADRs; corrected by an amendment ([ADR-006](decisions/ADR-006-frontend-runtime-config.md), 2026-11-23).
- **Foreign keys declared, never enforced.** *Published, the whole series.* The schema declares `ON DELETE CASCADE` over a connection that never turned foreign keys on, so deleting a post left its comments in the database; an earlier audit had confirmed the declaration, not the behavior. Found when qa-pipeline recorded its database choice (qa-pipeline [ADR-006](https://github.com/CarpinetiOctavio/forum-app-qa-pipeline/blob/main/docs/decisions/ADR-006-sqlite-and-unenforced-foreign-keys.md)); corrected here on every connection ([ADR-011](decisions/ADR-011-enforce-sqlite-foreign-keys.md), [`acb2211`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/acb2211)).
- **A permission grant with no effect.** *Published, cloud-deploy.* A rule taken from the predecessor's notes ([transferable knowledge](audits/cloud-deploy-legacy-transferable-knowledge-results.md), §2) required `packages: write` at the workflow level; every job declares its own permissions, so it reached no job (run `45336308644`). Found in the closing review; removed ([`1999360`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/1999360); [ADR-002](decisions/ADR-002-container-registry.md), amendment of 2026-11-24).
- **A Render API key in a public repository.** *Published, cloud-deploy-legacy.* A real `RENDER_API_KEY` was committed as a copy-pasteable example in `-legacy`'s `COMMANDS.md`, recorded in its ADR-007 (e). Found by a manual review; the key was replaced with a placeholder and rotated, a rotation supported only by indirect evidence: the secret's `updated_at`, 2026-07-02 ([audit](audits/cloud-deploy-legacy-audit-results.md), l.200). The two real `srv-…` service IDs next to it were redacted later, in `-legacy`'s `48b7189` (same audit, l.354–365). No gate checks for Render keys; it is declared as a limitation in the [README](../README.md).
- **A deploy script marked as verified.** *Found in review, cloud-deploy.* The script was accepted as verified after a syntax check only: `deactivated` was polled until timeout as if the service were still starting, and no HTTP status was checked, so a mistyped hook or an invalid key was retried for minutes and failed with a misleading message. An audit of that commit found both before the merge ([`0366411`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/0366411)). Lesson: a syntax check is not a behavior check.
- **A deploy that could not show what it deployed.** *Found in review, cloud-deploy.* The first deploys went by tag: the logs never showed a digest, and a rerun could move the tag while PROD waited for approval. Found before the merge; deploys pass the digest and log it ([`bfbf2e2`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/bfbf2e2); [ADR-007](decisions/ADR-007-render-deploy-mechanism.md), amendment of 2026-11-11).
- **A rollback check that counted its own deployments.** *Found in review, cloud-deploy.* The first rollback validation accepted digests from deployments created by the rollback workflow, which record `main`'s commit, not the image's: one rollback could make the digest of a commit never approved for PROD pass from then on. Found in the review of the branch; only deployments created by `ci.yml` count ([`06e737e`](https://github.com/CarpinetiOctavio/forum-app-cloud-deploy/commit/06e737e); [ADR-007](decisions/ADR-007-render-deploy-mechanism.md), amendment of 2026-11-23; [screenshot 08](screenshots/08-rollback-2-validation-accepts-ci-deployment.png)).
- **A pair validated one digest at a time.** *Published, cloud-deploy.* The rollback rule in `docs/rules/deployment.md` requires redeploying "a pair of image digests (backend and frontend) that already reached PROD from `main`", and [`rollback.yml`](../.github/workflows/rollback.yml) validates each digest on its own, so a backend and a frontend from different commits pass although that pair never ran in PROD together. Found in a cold reading of the README; the fix, checking that both digests come from the same deployment, is not applied, because it would mean changing the validation script and repeating the rollbacks with PROD approval. It is declared as a limitation in the [README](../README.md).

## A pipeline dependency out of support

- **Node.js 18 after its end of life.** *Published, ci-testing.* ci-testing's frontend jobs ran on Node.js 18 from a first commit made after 18's end of life (2025-04-30); the pipeline kept passing, so nothing flagged it. Found in the series audit; the jobs run on Node.js 24 LTS ([`d2d3838`](https://github.com/CarpinetiOctavio/forum-app-ci-testing/commit/d2d3838); ci-testing [ADR-004](https://github.com/CarpinetiOctavio/forum-app-ci-testing/blob/main/docs/decisions/ADR-004-ci-pipeline-design.md), amendment of 2026-11-12).
